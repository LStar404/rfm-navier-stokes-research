RFM–NS v8 现有阶段计时与资源使用复核

以下归因只读取已保存的元数据。高档薄入口 T72 有 50 条数值通过且采样
隔离合格的历史记录。融合 T9 是四个配对的顺序诊断，两个队列的范围、
实现和计时口径不同。未新增求解、采样、计时或硬件利用率观测。

薄入口的收益位于新进程进入求解之前。按同一区块的旧入口减最小入口，
RFM41 恒步、分段的新进程返回中位节省分别为 0.794 s、0.824 s，
Popen 到 READY 中位分别缩短 0.796 s、0.848 s，完整求解时钟反而微增
0.00155 s、0.00837 s。Legendre39 恒步、分段的 Popen 到 READY 分别
缩短 0.776 s、0.895 s。READY 在求解入口导入完成后发布。这个间隔也
包含解释器、动态库、请求读取、身份校验和通知传输。独立导入诊断中，
Gal 恒步、分段的导入中位数由 1.936/1.961 s 降至 0.980/1.042 s，
可作为入口依赖变薄的补充证据，不从独立诊断分母生成正式倍数。

主机准备含空间基和离散算子装配、NumPy/BLAS/LAPACK 或稀疏数值工作、
数组分配、边界及探针准备。分段 Galerkin 还在其中装配和预收缩各相位。
FD 稠密/带状线性预计算另计。运行时初始化含 CUDA 上下文或流、NVRTC、
驱动模块加载、符号绑定和库装载等，历史 T72 未单列 NVRTC。
推进是同步过的墙钟区间，含 GPU 内核、FFT、观测和宿主提交开销，
不能把它当作单一内核时间或纯 CPU 调用开销。单纯把 Python 编排改写
成 Rust 会改变入口和宿主调用成本，但调用同样 CUDA、cuFFT、BLAS 和
LAPACK 时没有直接减少它们的运算。这里没有 Rust 同口径实测。

只有在其余阶段完全不变时，消除一个已测阶段的墙钟预算才以该阶段为
上限。例如 RFM41 分段主机准备的观测中位为 58 ms，即便全消也只占
完整求解约 3.4%。这并不等于 58 ms 都是 Python 或可被消除。若只取消
NVRTC，其潜在节省包含在运行时初始化内。0.484 s 是该组完整初始化的
观测中位，包含仍必须支付的工作。阶段中位数独立取值，不拼成最短轨迹，
也不用观测最小值推断可达极限。

融合 T9 四个配置的主机准备变化不足 2 ms。融合内核让推进节省
0.0168–0.0299 s，但 NVRTC 与驱动加载的合计计时增加 0.253–0.621 s，
完整求解增加约 23%–69%。这把短程回退定位到编译/加载合计阶段，
不能分配其中多少是源编译、多少是驱动 JIT。PTX 缓存能在已验证命中
时直接跳过每次 NVRTC 源编译，仍要支付首次构建、每次读验、CUDA
上下文和模块加载，驱动还可能执行 PTX JIT。CPU 独立构建的单键 NVRTC
时间约 0.315–0.347 s（stock）、0.554–0.870 s（融合）。这是编译
阶段实测，不能直接从 GPU 求解钟扣掉。缓存 T9 在首个禁用缓存对照超时，
没有命中或空缓存 GPU 样本。按键摊销仅是成本核算，尚无整程缓存收益。

公平计时刻意串行，每次用一个新求解进程。该历史机器有 32 个逻辑 CPU，
求解进程固定在逻辑 CPU 4，BLAS 线程数固定为 1，监控独立固定在 CPU 6。
即使工作进程一直占满单逻辑核，按逻辑核计数也只相当于整机约 3.1%，
这既不是已测利用率，也不能代表异构核心的实际性能。在 GPU 驻留推进
时主机主要构造和提交任务、等待同步，整机 CPU 百分比并不衡量一次求解
的效率。单轨迹延迟看同精度双时钟。并发运行多个独立算例要比较达标
轨迹数/墙钟，并验证显存、GPU 相互竞争与资源开销。本轮没有同门槛的
业务并发吞吐实证，串行基准不能证明并发有利或无利。
