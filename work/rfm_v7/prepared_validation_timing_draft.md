# Prepared CUDA switch validation and timing draft

Freeze the exact solver, binaries, dependency closure, existing reference and control artifacts, telemetry implementation, dataset schemas, and randomized schedules before execution. The accompanying JSON is a proposed design. A final freeze requires a separate approved launch, an implementation audit, and a transport and identity test that performs no fluid solve.

## Qualify the implementations

1. Make the two preparation switches independent. `M` changes only the switched runtime from the old pair of CUDA modules to the single six-kernel module. `H` changes only host preparation from independent phase models to shared spatial data and distinct phase-dependent operators. Preserve the four-kernel uniform runtime. Demonstrate runtime selection with module counts and spatial construction counts, and bind module and phase-operator identities to each result. Rebuild all host state and create a fresh CUDA context within each solve. Preserve the user's operating-system and driver caches.
2. First compare the old and new runtime entry points at fixed states. For `M`, require the complete six-kernel parameter and output contract, including order, history, and bridge kernel. For `H`, compare the read-only coordinates, basis, lift, quadrature, and transforms separately from the per-phase operators. Require separate mutable history and work buffers, compare host and exported matrices before upload, and verify the phase-dependent factorization is still run for all required step sizes. Record bitwise agreement where present and finite scaled differences elsewhere. Exercise Euler start, both sides of the bridge, snapshot/probe samples, odd graph tails, and rollback on failed initialization. Any defect stops timing preparation.
3. Run the 26 new, untimed `T=72` trajectories in the JSON. At the middle resolution, the three new switch arms each use the five registered RFM seeds and Legendre. At the high resolution, the joint arm uses the same six identities. At the low resolution, run the joint arm for RFM seed 7331 and Legendre as two fixed failure controls. Keep all low cases in the accuracy table and omit them from the timing schedule. Any unexpected change in the low pass/fail status triggers investigation of numerical equivalence before freezing a timing cohort.
4. For each accuracy trajectory, compare all 21 implementation checkpoints and full probes to the matched CPU Recurrence schedule. Compare the new implementation directly to the archived old GPU switch trajectory on identical observations, using the same implementation gate. Audit the two fine references and their radial/angular/time composition separately. At all 19 physical times, on three grids and for each of four norms, score the direct error and switched uniform-anchor guard against the 0.5% ceiling. A timing arm must pass both. The guard is `anchor_error + (1 + anchor_error) * switched_vs_anchor`. Its entries must also bound the direct switched error up to the declared numerical tolerance. Verify sustained alternating wake probes. Evaluate every field at its saved physical time and on its registered grid. The off-grid observations are reserved for the implementation comparison.
5. Before timing, every method arm at that resolution needs exact matching qualification for all registered seeds, including the same CUDA FD implementation. Archived evidence may be reused when hashes, full precision, spatial configuration, implementation, rate, observations and tolerances match. The high uniform CUDA arm at rate 152 requires new six-identity verification if such evidence is absent. The high FD reference comparison uses the verified band implementation for FD184. The failed dense FD184 result remains in the accuracy archive.

## Time one registered cohort per eligible resolution

Use five randomized complete blocks, with the same RFM seed for every RFM arm in each block and seed 17 for Legendre and FD. Derive the order from the registered seeds and store all 55 middle and 40 high identities before launch. The high cohort checks scale transfer of the combined change. The middle cohort supports attribution to the two independent preparation changes. Launch separate fresh children serially under the same affinity mask, BLAS thread limits and GPU. Wait for child exit, serialization and scoring before the next launch. The monitor checks the complete fixed window, including the predeclared idle tail after the final solve. Publish every failed, incomplete and contaminated row and its evidence. Any failed numerical gate or rejected isolation window makes the affected cohort diagnostic only, and no row is replaced. The high cohort may proceed independently if its own predeclared gates pass and authorization is still current. Use only observations from the registered cohort to compute its paired statistics.

For every timed trajectory, archive the 19 physical observations and full probes. Check matched CPU fields and probes, both fine references, the switched anchor guard, wake, work counters, and method identity again. Compute the independent 21-time results from the pre-timing accuracy archives. On every CUDA arm, report context/module loading, host spatial and phase-specific preparation, upload, FFT plan and priming, graph capture, march, download, synchronization and release where these can be measured without overlapping intervals. Keep canonical elapsed times from the corresponding source and show setup/march alongside them. Use paired means for an additive phase decomposition and report any residual. Keep the two user-facing clocks distinct.

- Solver clock includes host model and factors, CUDA creation, full march and observations, synchronization, download, context cleanup, and model release. Identity handshake is before its starting boundary. Archive any intentional exclusion from the clock such as computing an audit hash.
- Fresh-process clock begins before `Popen` and ends when the parent receives the flushed synchronized completion marker after cleanup and before NPZ write. Identity handshake is included. Use the same handshake for every method, record its separately measured overhead, and leave it in this clock. Preserve the original marker and PID identity. Neither this measurement nor the solver clock requires clearing machine caches.

Within each middle block, compute the paired time ratios `old/M`, `H/both`, `old/H`, `M/both`, `old/both`, and `uniform/both` on both clocks. Report the same blockwise module and host contrasts for preparation and march in seconds. Compute the factorial interaction for each stage as `T_both - T_M - T_H + T_old`. The high block reports `old/both` and `uniform/both` as joint comparisons. At both scales, report within-block FD176/Galerkin ratios and Legendre/RFM ratios using matching implementations and schedules. The same high blocks include FD184 to show the scale and accuracy trend. Record all five values, median, range and directional wins. Display actual errors alongside the common ceiling. For each eligible method, report the fastest observed registered configuration separately on each clock, list the full candidate range, and label the selection descriptive. Only claim consistently faster for a preregistered pair when all five blocks favor the candidate on both clocks and the median ratio is at least 1.05 for each. Treat this as a practical reporting rule. Stop after one attempt per eligible scale, or at the previously authorized account-budget boundary. The result table covers the registered arms.

The previous 60-row worker took about 685 seconds, including about 183 seconds outside the parent fresh-process clock. For planning only, the previous middle GPU controls had maximum per-row fresh times of 3.58–5.27 seconds. A 600-second middle window and a 480-second high window are initial proposals. Validate budgets against non-formal saved phase and I/O evidence and fix them before any accepted run. Finishing outside the registered window yields diagnostic timing even when every trajectory passes.

## Identify cohort processes independently of lifetimes

The earlier monitor consulted a coordinator's live state and command match after collecting a process snapshot. A coordinator/child exiting between the snapshot and that check could cause the child's CPU activity to be assigned to the external category. Keep the earlier monitoring evidence intact. The new monitor needs stable identity before any worker does numerical work.

1. Obtain each coordinator and child identity from its actual Windows process handle, with `GetProcessTimes` returning the full creation FILETIME in 100 ns ticks. Register this identity, parent identity, slot, launch monotonic time, expected path role, and eventual exit in an append-only ledger. Use a run token and a startup barrier. Launch the child with the normal timed `Popen`, register the handle and admit it via its already open pipe, then let its solver clock start. Child echoes the registered slot/token and timing marker. Use the same wrapper handshake for the coordinator, with no computation until its exact identity is registered. Retain handles through wait and record exit times even when a process leaves a monitor snapshot during enumeration. PIDs and creation timestamps are published with slot and role, while command lines and user paths are kept out of the evidence.
2. Every ten seconds collect raw process snapshots with the same native `GetProcessTimes` identity source, parent PID, classification short label, raw kernel/user CPU counters and sample UTC/monotonic interval. Record unresolved processes and snapshot failures. Keep the original snapshots. For observed Python processes, open query-only handles and retain them through at least the next sample when possible, so a process that exits after one observation can still contribute its final CPU delta. Preflight retains only recognized idle background identities within the registered thresholds and low GPU load. Record scope and any limit from inaccessible or short-lived processes. Windows GPU endpoint counters are aggregate coverage, not per-process telemetry.
3. At close, classify sampled activity by exact `(PID, creation FILETIME)` join to the immutable registration and launch/exit ledger. Check exact slot identities, unique index/parent relationships, valid time intervals, parent waits and serial measured spans. A child recorded in a snapshot is a cohort member even if its controller exits before the snapshot is analyzed. Never remove a sample or mark a process as cohort based on PID alone, name, or observed runtime effect. Unresolved relevant Python identities or missing ledger coverage make isolation unverified. New, non-cohort Python activity above the frozen threshold still rejects isolation. Keep threshold logic unchanged unless a further pre-run protocol revision is approved.
4. Before authorization, run a transport-only identity test with a short-lived registered child that exits while an observation is processing, an unrelated short Python process with measurable CPU, and synthetic PID-reuse/invalid-ledger checks. Verify the first matches its ledger, the second remains external, and ambiguous identities reject isolation. Document sampling coverage and timing effects. Monitoring records can support the absence of observed external activity within their scope and cannot rule out all system or between-sample work.
